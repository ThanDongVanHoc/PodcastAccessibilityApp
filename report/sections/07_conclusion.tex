\section{Conclusion}

Accessibility in Compose is not a set of rigid rules but a flexible guidance over the semantics tree at every level: naming
and hiding nodes correctly (§\ref{sec:core}), then grouping, ordering, and consolidating their
actions (§\ref{sec:adv}). The payoff for work taken is measurable in convenience: a podcast card drops from six focus stops to
one, the resume banner is announced first, and playback state is spoken the instant it changes, so
a TalkBack user can completes the full Discover~$\rightarrow$~Detail~$\rightarrow$~Player flow without sight.

Verification matters as much as construction (§\ref{sec:test}): TalkBack judges the listening
experience, Scanner and ATF triage mechanical defects, Layout Inspector explains structure, and
Compose tests lock semantics against regressions. No layer's result suffices alone, and they show the element that \textbf{may} have problem in accessiblity, as shown in the Agoda case study.
The lesson is to integrate accessiblity in parallel with developing the interfaces . Prefer pre-made-accessibility-verified, such as the Material Design, for
their default semantics, add custom semantics only where the design forces it, and test with the
assistive technology that users actually use.
