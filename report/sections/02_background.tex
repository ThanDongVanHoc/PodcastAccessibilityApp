\section{Background}

\subsection{Accessibility as a legal requirement}

Accessibility has moved from ``nice to have'' to a mandatory features in many markets. The
\textbf{European Accessibility Act (EAA)} argues that a common accessibility standard benefits
everyone: disabled users gain fair, unified accommodation and real competition between providers,
while companies gain a larger customer base and a single ruleset to build against. All EU member
states incorporated the EAA into national law from June~2022, leaving the exact mechanism (directive,
act, or regulation) and implementation to each country; the shared principle is that products offered in the EU must
adhere to the common accessibility requirements.

The technical yardstick behind most of this legislation is the \textbf{Web Content Accessibility
	Guidelines (WCAG~2.2)}. Although WCAG is written for the web, its success criteria are applied to
native software through \emph{WCAG2ICT} and platform-specific mobile guidance. Because a podcast app
is not a web page, we treat WCAG as technology-neutral guidance and map each criterion onto its
Android equivalent on our own interpretation.
\subsection{The POUR principles}

WCAG organises accessibility around four principles, remembered by the acronym \textbf{POUR}
(Figure~\ref{fig:pour}). They are the lens through which we evaluated every screen of our app.

For a media player they can be interpreted as:
\begin{itemize}
	\item \textbf{Perceivable}: labelling every transport icon and keeping duration text high-contrast
	\item \textbf{Operable}: play, seek, and bookmark must  all work from TalkBack;
	\item \textbf{Understandable}: the play button announces whether it is playing or paused;
	\item \textbf{Robust}: we expose a correct semantics tree rather than relying on composition tree to provide context
\end{itemize}


\subsection{How Android exposes the UI to assistive technology}

The single most important idea for an Android developer is that the screen a sighted user sees and
the structure a screen reader traverses are \emph{two different trees}
(Figure~\ref{fig:trees}).

\begin{itemize}[leftmargin=1.4em]
	\item The \textbf{Composition / layout tree} is the visual render hierarchy. Its nodes are boxes,
	      text, and images, ordered by where they are drawn on screen.
	\item The \textbf{Semantics tree} runs in parallel and describes \emph{meaning}: each node carries a
	      name/label, a role, a state, and the actions it supports. This is the only thing assistive
	      services can read.
\end{itemize}

Assistive services such as TalkBack (screen reader) and Switch Access run as background
system services. They subscribe to the merged semantics tree, convert each node into speech or
a scan target, and translate user gestures back into actions. A screen can therefore look perfect yet
be unusable if its semantics tree is missing, wrong, or badly ordered. Therefore, the thing we need to take account of when developing inclusive application in Android is how to shape the sematic tree correctly.
To discuss on the technique, we will utilize the Jetpack Compose UI framework.

\subsection{Jetpack Compose}

Jetpack Compose is Android's modern declarative UI toolkit (conceptually similar to React). UI is
described by composable functions. The interface is a function of states, state changes trigger recomposition and redraw of UI. Compose
generates the semantics tree from \code{Modifier.semantics} blocks and from the built-in semantics of
Material components, which gives us fine-grained, code-level control over exactly what assistive
technology perceives.
